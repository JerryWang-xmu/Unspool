# Unspool Constitution

## Core Principles

### I. 通用 Agent 闭环优先

- 用户必须能够在不创建团队、不邀请成员、不开启共享的情况下，完成真实的个人 Agent 任务。
- 个人任务必须支持工具、文件、产物、历史与恢复，并与共享任务保持一致的执行语义。
- 不得以协作演示或 Federated Beta 进度为由，推迟或豁免 Stable 发布工作。
- 协作功能必须默认保护个人凭据、草稿、偏好与未选择内容，只有用户显式选择后才可共享。

**理由**：如果底层 Agent 不能独立完成真实工作，共享执行就没有持久价值。个人可用性是
产品底座，而不是协作功能的简化演示。

### II. 最小权限与本地授权终裁

- 访问必须默认拒绝，并针对任务、目的、资源、操作、接收方与期限获得明确、有限的许可。
- 读取、模型外发、成员可见、公共共享与跨域传播必须分别授权，任何一项均不得隐式推出
  另一项。
- 资源所有者必须保留本人节点的最终决策权，包括批准、缩权、撤销、暂停与隔离；服务器、
  管理员或工作间权限不得覆盖该决定。
- 权限必须默认只读、短期、不可转让且不可升级；资源、目的、操作或接收方发生实质变化时，
  必须重新授权。
- 派生结果必须继承最严格的来源限制，只有具备权限的所有者显式复核后才可降低限制。

**理由**：Unspool 将设备级或账号级的宽泛信任转化为可验证的任务级信任。集中协调不得
演变为集中占有各参与方的数据与权限。

### III. 人类控制与明确责任

- 每个工作间同一时间必须至多只有一名当前操作者和一个活动任务；讨论、指令建议与直接
  Agent 指令必须始终可区分。
- 高风险副作用必须在执行前获得所需批准；离线、关闭页面、超时或网络异常均不得视为批准。
- Agent 不得自行确认业务完成、自行确认关键结论或扩大自身权限。
- 交接必须显式确认责任；接手前准备必须默认私人、只读，不得中断正在运行的任务。
- 每项指令、审批、接管、确认、例外与导出都必须记录责任人和时间。

**理由**：模型建议不等于组织授权。明确的人类责任能够防止静默副作用，并使工作可以跨
人员与时间安全延续。

### IV. 证据、署名与诚实状态

- 关键结论必须保留来源、确认历史、有效状态、适用范围与已知依赖；有来源不得被表述为
  已经证明为真。
- 来源变化、冲突、撤销与证据缺失必须呈现可见的复核影响；系统不得静默推翻决策或抹除
  既有历史。
- 成功、失败、取消、撤销与结果未知必须如实区分；不确定的副作用不得被描述为确定结果，
  也不得自动重放。
- 历史贡献、审批、产物、回执与例外必须在角色变化、归档或成员退出后保留署名与版本。
- 撤销必须阻止新的访问，但不得宣称召回已合法获取的副本；删除与导出必须如实说明历史
  记录和审计边界。

**理由**：产品承诺的是可追溯、可复核的工作，而非虚构的确定性。用户必须能够区分已记录
事实、人工判断与未解决风险。

### V. 独立验证与分轨交付

- 每项特性在进入实施规划前，必须具备可独立测试的用户场景、可测试需求与可衡量结果。
- 安全与权限不变量必须具备可执行的回归覆盖和对抗性验收检查；不得仅以界面表现证明
  规则已经生效。
- Stable 与 Federated Beta 必须分别进行启用、验收、发布与回滚决策；Beta 必须可选，且
  不得削弱 Stable 行为。
- Federated GA 必须满足 PRD 规定的真实使用证据、独立威胁模型评审、第三方安全测试，
  且未解决的严重或高危问题数量必须为零。
- 发布声明必须与已验证的平台和能力一致；不支持的行为、回执缺口与已知限制必须公开，
  不得以笼统的安全措辞掩盖。

**理由**：一次成功演示不能证明安全、可靠或具有产品价值。声明必须在其实际生效边界上
由独立证据重复验证。

## 安全、隐私与合规约束

- 工作间成员、Runner 访问、角色权限与资源 Grant 必须在每条访问路径上执行，包括搜索、
  时间线、错误、日志、导出与分析。
- 凭据、私人接手问题、敏感工具参数、受限路径与资源正文不得进入共享记录或产品分析，
  除非其显式可见性规则允许；分析必须默认仅采集行为元数据。
- 联邦能力必须默认关闭，并要求团队、工作间、节点三级启用及具体资源授权；已过期、
  已撤销或预算耗尽的权限不得在重试、升级或重启后复活。
- 在声明的 Beta 边界内，任意命令执行、隐式凭据或环境继承、直接写回，以及通过内容或
  派生结果绕过权限的行为必须保持阻断。
- 已接受的操作必须在客户端刷新和重连后保持不丢失、不重复执行；客户端断线本身不得
  停止正在运行的任务。
- Unspool 自有源代码发布必须附带 MIT 许可证和准确版权声明。第三方软件、资产、文档、
  模型与品牌必须保留各自许可和使用边界，并具备可审计的依赖与资产清单。
- PI-Desktop 必须仅作为抽象交互参考，除非特定复用另行通过 LGPL-3.0 合规评审。来源不明
  或无权使用的内容必须阻断发布。

## 交付流程与质量门禁

1. **先定义需求，再设计方案**：产品工作必须从用户价值、范围边界、优先级场景、验收条件
   与可衡量结果开始。技术文档不得静默改变 PRD 定义的用户语义。
2. **先验证规则，再编写实现**：每项实现或修正必须先定义可观察的预期结果。新行为与
   回归修复必须先在适当边界形成 failing check，再完成修改，并在通过后保留该检查。
   纯文档或纯视觉工作必须预先定义等效的人工评审证据。
3. **验证实际执行边界**：权限、审批、撤销、传播、幂等、持久化与结果未知规则必须在
   其实际执行位置测试，不得只检查界面或模拟出期望答案。
4. **审查完整影响**：涉及共享状态、授权、证据、档案或联邦能力的变更，必须覆盖跨角色、
   离线、重试、升级与历史记录审查。引入新依赖或资产时，必须同步更新合规清单。
5. **分别满足发布门禁**：对应 Stable 或 Beta 发布前，所有适用的 P0 需求与 UAT 场景必须
   通过。指标必须采用 PRD 口径；在线状态、演示和原始活动量不得替代有效协作或真实任务
   完成。
6. **关键安全失败必须停止**：确认发生授权绕过、未授权泄露或传播、撤销后访问、无法解释
   的审计缺口或静默扩权时，必须停止受影响版本发布及新 Grant，同时保留证据和用户的
   合法导出能力。
7. **例外必须留痕**：任何获准的产品例外必须记录责任人、范围、理由、风险、期限和补救
   措施。不得通过移除安全不变量或历史证据来制造通过结果。

## Governance

- 本宪法约束设计、实现、评审、验证与发布。PRD 定义产品范围和语义，技术方案与项目约定
  必须同时遵守二者；冲突必须通过产品和治理评审显式解决，不得静默处理。
- 修订提案必须包含理由、受影响原则、兼容性影响、所需规格或流程更新、迁移需求与验证
  证据。产品、研发、安全和测试评审者必须审查各自受影响领域。
- 宪法版本采用语义化版本：向后不兼容的删除或重定义提升 MAJOR；新增或实质扩展原则或
  章节提升 MINOR；非语义澄清提升 PATCH。获批修改必须同步更新版本和修订日期。
- 批准日期记录首次正式采用时间，后续修订不得改变；最后修订日期必须使用 ISO
  `YYYY-MM-DD` 格式记录最近一次获批的治理变更。
- 每次实现与发布评审必须核查适用原则、安全不变量、验收证据和第三方义务。评审者必须
  记录例外，不得将未验证工作视为合规。
- Sync Impact Report 仅为评审临时材料，必须在修订后的宪法提交前移除；它不能替代修订
  理由或批准记录。
