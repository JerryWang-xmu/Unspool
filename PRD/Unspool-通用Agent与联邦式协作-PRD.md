## 1. 产品概述

### 1.1 背景

越来越多专业工作开始由个人在本机使用 Agent 完成。随着任务时间变长、工具调用增多、结果影响变大，单人会话逐渐暴露以下问题：

- 工作过程封闭在个人终端中，其他成员只能看到转述或最终结果。
- 临时接手需要重新解释背景，甚至重新执行已经完成的调查。
- 多人各自询问 Agent，产生重复工作、重复费用和不一致结论。
- 任务执行与文件产物分散，团队难以形成统一进展认知。
- 高风险操作缺少团队审批与责任记录。
- 本机文件、凭据和网络环境不宜直接共享，但又需要支持团队协作。
- 单 Runner 工作间仍要求文件与执行环境集中在一处，无法覆盖跨设备、跨客户环境和外部专家短期参与。

### 1.2 产品定义

Unspool 首先是一个可独立使用的通用 Agent 产品。个人用户通过独立 GUI 客户端连接本地／VPC Runner，即可完成多轮对话、工具调用、文件处理、持续任务、过程查看、产物管理和历史恢复，不必先创建团队或邀请其他成员。

在此之上，Unspool 才是一个共享 Agent 工作系统。用户可以将个人任务开启为共享工作间，或直接创建团队工作间，共同维护任务上下文，查看同一个 Agent 的执行过程，按明确规则交接操作权、审批高风险动作，并沉淀可追溯的任务记录与产物。

在此之上，可选的 **Federated Beta** 允许每位协作者连接本人本地／VPS 贡献者节点，把指定文件快照和受控工具按任务、限时、可撤销地贡献给同一工作现场。协调环境可以集中，但不能因此天然拥有各节点全部权限。

在共享、交接和审批等基础能力之上，Unspool 用两个功能形成差异化：

- **活证据：** 让关键事实和结论绑定依据、责任人和有效状态；依据变化时，能找到受影响的决策、产物和完成判断。
- **无扰接手：** 接手者在正式接受责任前，可以私下向 Agent 提问和核对依据，不中断当前任务，也不污染公共会话。

一句话销售表达：**共享 Agent 的基础价值是让团队看到“Agent 做了什么”；Unspool 进一步让团队知道“哪些结论有据可依、哪些需要复核，以及下一个人能否在没有额外同步会的情况下接住工作”。**

### 1.3 核心价值

> 将“某个人正在使用 Agent”转变为“团队正在共同推进一项工作”。

| 价值对象 | 核心价值 |
|---|---|
| 个人专业用户 | 不依赖团队协作配置，也能完成完整的通用 Agent 工作并管理本地／VPC 任务 |
| 任务负责人 | 工作过程可见、责任清晰、随时可交接 |
| 执行成员 | 无需反复解释背景，能够获得同事补充的事实与判断 |
| 接手成员 | 快速理解目标、已做工作、当前阻塞和下一步；正式接手前可独立核实疑问 |
| 复核与决策者 | 能看到关键结论的依据、有效状态和影响范围，而非只阅读 Agent 总结 |
| 审批与管理人员 | 高风险动作事前可控，事后可追溯 |
| 资源所有者 | 不必交出整台设备或长期账号，可按目的、期限和接收方贡献最小环境能力 |
| 团队 | 减少重复劳动，将一次性会话沉淀为可复用工作记录 |

### 1.4 产品原则

1. **共享工作，而不只是共享聊天。** 目标、上下文、执行、产物和责任记录都属于共享对象。
2. **先保证可理解，再追求实时炫技。** 新成员能否看懂和接手，比多人同时输入更重要。
3. **协作有边界。** 讨论、补充材料、操作 Agent、审批高风险动作是不同权限。
4. **执行与在线状态解耦。** 某个成员离线不应无故终止正在运行的任务。
5. **危险动作默认需要确认。** 系统不能将模型建议直接等同于团队授权。
6. **所有关键过程可追溯。** 能回答“谁发起、谁补充、谁操作、谁审批、产生了什么”。
7. **有来源不等于已经证实。** 产品帮助用户追踪依据与有效性，不把引用自动包装成事实。
8. **准备接手不应打断正在工作的人。** 接收者可以先独立理解、提问和核对，再决定是否承担操作责任。
9. **通用平台也要完成真实工作。** MVP 不以多人演示为目标，而以真实任务完成和交接为目标。
10. **通用能力先于协作配置。** 用户无需邀请他人即可独立完成任务；需要协作时，再自然开启共享。
11. **开放不等于随意复用。** 自有代码以 MIT 开源，同时尊重第三方代码、设计资产、商标和许可证边界。
12. **贡献能力，不交出设备。** 节点配对不等于资源共享，服务器不能绕过资源所有者的本地授权。
13. **共享状态，不默认共享原文。** 读取、模型外发、成员可见和跨节点传播分别授权。
14. **撤销不等于召回。** 撤销停止未来访问，已经合法获取的副本按原许可处理。
15. **Beta 不转移安全责任。** 默认关闭、边界明确、可独立停用，并有公开转正门槛。

### 1.5 与 pi Agent 的关系

产品应复用 pi Agent 已有的持续会话、上下文管理、工具调用、任务执行、运行中纠偏和后续指令排队等能力。Unspool 的产品增量主要是：**独立 GUI、通用 Agent 工作体验、本地／VPC Docker Runner、个人任务转共享、多人身份、共享工作间、结构化上下文、操作权交接、团队审批、任务记录、活证据、无扰接手和协作体验。**

本 PRD 只把 pi 作为产品能力基础，不限定其具体接入方式。

## 2. 产品目标与成功标准

### 2.1 用户目标

- 个人用户无需创建团队或邀请成员，即可使用完整通用 Agent 能力。
- 团队能够围绕同一个 Agent 会话完成真实任务。
- 资源所有者能够在不开放整台设备的情况下，贡献指定文件、快照或受控工具。
- 团队能够完成跨所有者、跨环境的真实任务，并明确知道数据流向。
- 任何授权成员都能快速理解当前工作状态。
- 操作者能够将任务安全交给另一名成员，而不必重建会话。
- 接手者能够在不打断当前操作者的情况下，先核实背景、依据和风险。
- 成员能够判断关键结论当前是否可信，以及依据变化后需要复核哪些工作。
- 成员可以贡献信息与判断，但不必获得完整操作权限。
- 团队能够在高风险动作发生前进行审批。
- 任务结束后，过程、决策与产物可以统一查看和导出。

### 2.2 业务目标

- 验证“多人共享 Agent 工作现场”是否比多个私有会话更高效。
- 验证通用协作能力能否脱离单一行业场景独立成立。
- 找出最高频的协作行为，为后续工作流模板和垂直版本提供依据。
- 建立可扩展的团队使用基础，而非一次性分享链接功能。
- 验证“可信结论”和“低打扰交接”是否比基础共享功能更能形成付费理由。
- 为后续进入高价值、高复核成本的工作流建立明确的产品壁垒。
- 通过 MIT 开源降低试用、审查和私有化部署门槛，建立透明的第三方合规与社区使用基础。
- 验证联邦式环境协作是否解决集中上传难以替代的高价值任务，并形成可持续商业服务。

### 2.3 北极星指标

**每周多人有效协作工作间数量。**

一个工作间只有同时满足以下条件才计入：

1. 当周至少完成一个 Agent 任务；
2. 至少两名不同成员产生有效协作行为；
3. 有效协作行为包括提交或采纳 Agent 指令、维护共享上下文、确认或复核关键结论、完成任务交接、审批高风险动作；仅登录、围观和在线不计入。

**Federated Beta 补充北极星：每周完成的真实多环境任务数。** 至少两名不同资源所有者的节点作出有效贡献，且 Grant、访问回执和结果确认完整，才计入。

### 2.4 试点成功标准

以 5 个试点团队、每队至少 5 个真实任务为最低样本：

| 维度 | 目标 |
|---|---|
| 团队激活 | 至少 4 个团队在两周内完成首个双人协作任务 |
| 个人可用性 | 至少 80% 的新用户无需团队配置即可完成首个个人 Agent 任务 |
| 共享转化 | 记录个人任务开启共享的比例及其后续有效协作情况，判断是否形成自然增长路径 |
| 协作真实性 | 至少 50% 的试点工作间达到“多人有效协作”定义 |
| 交接效率 | 接手者恢复任务背景的中位耗时较原流程下降至少 50% |
| 无扰接手 | 至少 50% 的交接使用该功能；其准备时长和向原操作者追问次数的中位数均比普通交接低至少 30% |
| 证据质量 | 试点“完成”任务的关键结论有效证据覆盖率不低于 80% |
| 重复劳动 | 因交接而重复描述任务背景的中位次数下降至少 30% |
| 过程可控 | 所有被定义为高风险的动作都有批准、拒绝或超时未执行记录 |
| 用户理解 | 至少 80% 试点成员能正确区分“讨论”“指令建议”“直接操作 Agent” |
| 多环境价值 | 至少 3／5 联邦试点团队完成多个真实多所有者节点任务，并出现集中上传难以替代的价值 |
| 授权可理解 | 至少 80% 资源所有者能区分读取、模型外发、成员可见和跨域传播，并独立配置常见 Grant |
| 安全 | 无越权访问、跨工作间数据暴露或明文凭据进入共享记录的事故 |

## 3. 目标用户与核心场景

### 3.1 目标用户

首要用户包括已经使用 Agent 处理专业工作的个人，以及 2～20 人专业团队，包括研发、数据分析、安全、技术咨询和内部自动化人员。个人通用 Agent 是日常使用入口，多人协作与团队治理是主要商业价值验证方向。

MVP 不绑定具体行业，但试点任务应至少满足以下两项：

- 持续时间较长，无法一次问答完成；
- 需要两人以上参与或接力；
- 背景复杂，接手成本高；
- 需要调用工具或产生文件；
- 操作具有风险，或结果需要复核。

### 3.2 用户角色

| 角色 | 主要诉求 | 典型行为 |
|---|---|---|
| 团队管理员 | 管理团队和 Runner | 管理成员、配置可用 Runner、设置默认安全策略 |
| 工作间负责人 | 对任务结果负责 | 创建工作间、邀请成员、确定目标、结束与归档 |
| 操作者 | 推进或接手任务 | 操作 Agent、纠偏、停止、维护共享上下文 |
| 协作者 | 提供专业信息和判断 | 参与讨论、上传材料、维护本人贡献、提出指令建议 |
| 资源所有者 | 决定本人节点资源的读取、执行、外发、传播和撤销 | 配对节点、选择资源、批准 Grant、暂停或隔离 |
| 外部专家 | 在限期范围内贡献知识或环境能力 | 使用短期身份与短期 Grant，不获得长期访问 |
| 审批人 | 控制高风险副作用 | 查看动作及理由、批准或拒绝 |
| 复核者 | 判断关键结论能否继续被依赖 | 确认结论、核对来源、处理失效影响 |
| 观察者 | 了解进展和结果 | 只读查看任务过程与产物 |

资源所有者、外部专家、审批人和复核者均可与操作者或协作者身份叠加；资源所有者权限独立于工作间管理权限。

### 3.3 核心使用场景

| 场景 | 当前痛点 | 期望结果 |
|---|---|---|
| 个人独立完成任务 | 不想为每次使用配置团队、成员和共享权限 | 打开 GUI、选择 Runner 与模型后即可开始完整 Agent 任务 |
| 个人任务升级为团队协作 | 任务做到一半才发现需要同事参与 | 选择性共享现有历史、上下文和产物，不重建任务 |
| 跨机联合排障 | 代码、测试和日志需要集中上传，环境权限粗糙 | 各方分别贡献代码快照、测试工具和日志查询 |
| 客户环境短期专家诊断 | 需要长期 VPN、账号或大量文件复制 | 只提供完成任务所需的短期窄范围能力 |
| 多人共同推进长任务 | 每个人都在自己的会话里重复调查 | 所有人围绕同一任务进展协作 |
| 中途接手 | 依赖口头转述，遗漏已做工作 | 通过交接摘要和完整记录快速继续 |
| 接手前仍有疑问 | 只能打断原操作者，或在公共频道提出基础问题 | 先私下向 Agent 核实，再决定是否接手和公开哪些结论 |
| 关键依据发生变化 | 旧结论仍被当作当前事实使用 | 标记待复核，并列出受影响决策、产物和完成判断 |
| 专家临时参与 | 专家只需提供判断，不应接管整个任务 | 以协作者身份补充材料或提出建议 |
| 高风险工具操作 | 模型可能直接修改文件或执行命令 | 由授权成员查看并批准后才执行 |
| 异步查看进展 | 任务运行时无法随时询问负责人 | 成员随时打开工作间查看最新状态 |
| 任务结束复盘 | 对话、文件、审批和结果分散 | 统一查看、搜索和导出任务档案 |

### 3.4 关键用户故事

1. 作为个人用户，我希望无需创建团队或邀请成员即可开始并完成 Agent 任务，以便把 Unspool 作为日常通用工具。
2. 作为工作间负责人，我希望定义目标、完成标准和参与者，以便团队对“完成”有共同理解。
3. 作为个人任务发起者，我希望在需要同事参与时选择性开启共享，以便保留已有工作而不泄露私人偏好和草稿。
4. 作为操作者，我希望使用同一个持续会话推进任务，以免其他成员看到互不相关的私有对话。
5. 作为协作者，我希望只补充事实和提出建议，而不必承担误操作 Agent 的风险。
6. 作为接手者，我希望先看到当前目标、关键决策、最近进展、待办和阻塞，再决定是否继续执行。
7. 作为审批人，我希望看到工具将做什么、影响什么、由谁发起，再批准或拒绝。
8. 作为观察者，我希望不打扰执行者也能查看实时状态和最终结果。
9. 作为负责人，我希望任务过程可以导出，以便复盘、合规检查或移交给团队外成员。
10. 作为复核者，我希望看到关键结论所依赖的来源、确认人和有效状态，以便判断它现在能否继续使用。
11. 作为接手者，我希望在正式接受前私下向 Agent 提问，以便减少无效同步会，并避免把尚未公开的准备过程带入公共会话。
12. 作为资源所有者，我希望只贡献指定能力并能随时撤销，以便参与协作而不交出设备控制权。
13. 作为审批人，我希望分别审批模型外发和跨节点传播，以便防止一次读取授权被隐式扩大。
14. 作为商业试点负责人，我希望有明确 Beta 边界、回滚条件和审计回执，以便评估能否用于真实客户任务。

## 4. MVP 范围与优先级

### 4.1 优先级定义

- **P0：** MVP 上线必须具备，缺失会导致核心流程不成立或存在明显风险。
- **P1：** 试点期间可补充，不影响首个完整闭环。
- **后续：** 已识别价值，但明确不进入本次 MVP。

### 4.2 功能范围总表

| 模块 | 功能 | 优先级 |
|---|---|---|
| 通用 Agent | 多轮任务、模型选择、工具调用、持续会话、个人历史与产物 | P0 |
| 独立 GUI | 个人与共享模式、任务时间线、工具与文件、审批、设置和状态反馈 | P0 |
| Docker Runner | 本地／VPC Docker 部署运行、状态可见、数据持久和升级保护 | P0 |

| 开源合规 | MIT 许可证、第三方清单、设计来源记录和发布审查 | P0 |
| 联邦 Beta 开关 | 团队、工作间、节点三级启用，默认关闭与独立停用 | Beta P0 |
| 贡献者节点 | 配对、所有权、支持状态、撤销与隔离 | Beta P0 |
| 资源与 Grant | 文件快照、固定工具、任务级授权、期限与预算 | Beta P0 |
| 跨域数据流 | 模型外发、成员可见、跨节点传播和派生结果限制 | Beta P0 |
| 本地安全控制 | 活动暴露、访问回执、预算、Patch 和结果未知 | Beta P0 |
| 团队与成员 | 团队创建、成员邀请、角色与审批权限 | P0 |
| Runner | 查看可用 Runner、状态与适用范围 | P0 |
| 工作间 | 创建、配置、加入、归档 | P0 |
| 共享上下文 | 目标、完成标准、事实、决策、约束、待办、参考材料 | P0 |
| 人际协作 | 讨论、成员在线状态、指令建议 | P0 |
| Agent 操作 | 开始、运行中纠偏、后续排队、停止 | P0 |
| 操作权 | 申请、交接、离线后接管、负责人强制接管 | P0 |
| 过程可见 | 实时输出、工具活动、状态、阻塞、用量 | P0 |

| 任务模板 | 保存和复用常见目标、上下文及审批配置 | P1 |
| 工作间统计 | 成员贡献、任务耗时、交接和成本概览 | P1 |

### 4.3 明确不在 MVP 范围内

- 面向某个行业的专用知识库或业务连接器；
- 同一工作间内多个 Agent 并行执行；
- 自动拆分任务、自动组织多 Agent 协作；
- 多人同时无约束地直接操作 Agent；
- 跨工作间的自动组织记忆与知识图谱；
- 共享文档的多人实时共同编辑；
- 任意历史点的会话与工作区一键分叉；
- 公共云托管 Runner 和商业计费系统；
- 与 Slack、飞书、邮件等外部平台的通知集成；
- 自动监测所有外部数据源的变化，或由系统自动判定事实真伪；
- 在接手准备阶段复制完整 Runner或执行真实工具；
- 移动客户端；
- 任意宿主机 Shell、默认直接写回、长期目录同步和内部端口映射；
- 把多节点目录伪装成透明统一文件系统；
- 以敏感词扫描、Docker 或“零信任”名称替代实际权限与传播控制。

## 5. 核心概念与统一用语

| 名称 | 定义 |
|---|---|
| 个人任务 | 仅由当前用户使用的完整 Agent 工作，不要求配置团队或共享成员 |
| 开启共享 | 将个人任务中的选定历史、上下文和产物转为团队工作间的过程 |
| 独立 GUI 客户端 | 每名用户独立使用的图形界面，承载个人与共享 Agent 工作 |
| 团队 | 成员、Runner 和默认管理策略的边界 |
| Runner | 用户指定的本地或 VPC 工作位置，Agent 在其中使用授权资源完成任务；支持 Docker 部署运行 |
| 工作间 | 团队围绕一项持续工作共享的空间，包含目标、上下文、讨论、Agent 会话、任务和产物 |
| 任务 | 一次明确的 Agent 执行过程，可包含运行中纠偏和后续排队指令 |
| 当前操作者 | 当前有权直接操作 Agent 的成员，其他成员仍可按权限讨论和贡献 |
| 讨论 | 人与人之间的交流，默认不提供给 Agent |
| 指令建议 | 建议 Agent 做什么，需当前操作者采纳后才生效 |
| Agent 指令 | 直接被 Agent 接收并影响任务执行的内容 |
| 共享上下文 | 团队确认后供成员查看、并可选择提供给 Agent 的结构化信息 |
| 关键结论 | 会显著影响后续决策、完成验收或外部行动的事实、判断或决定 |
| 活证据 | 与关键结论绑定的来源、确认人、有效状态、适用范围和复核记录 |
| 无扰接手 | 接收者正式接受操作权前的私人只读准备过程，不影响公共会话和当前任务 |
| 产物 | Agent 生成或成员上传、与任务相关的文件和结果 |
| 贡献者节点 | 资源所有者本地／VPS 上的受控环境入口，配对不等于资源共享 |
| Grant | 面向任务、目的、资源、操作、接收方和期限的能力授权，默认只读且不可转发 |
| 快照 | 某时间点的明确资源版本，联邦任务默认读取快照而非无声跟随实时变化 |
| 节点 Artifact | 经许可离开来源域的结果，保留来源、版本、所有者和可见范围 |
| 模型外发 | 将获批原文或摘要发送给指定模型接收方的独立许可 |
| 跨域传播 | 数据从一个所有者域进入另一节点、成员、公共区或外部系统的行为 |
| 高风险动作 | 可能修改数据、改变外部状态、消耗重要资源或产生其他明显副作用的工具动作 |
| 工作间档案 | 任务结束后可查看和导出的完整过程记录 |

## 6. 核心业务流程

### 6.1 通用 Agent 个人主流程

**打开独立 GUI → 选择本地／VPC Runner 与模型 → 新建个人任务 → 输入目标或问题 → 查看 Agent 输出与工具活动 → 按需审批 → 管理文件与产物 → 保存并随时继续历史任务。**

个人模式必须提供完整任务闭环，不能把关键 Agent 能力锁定在“先创建团队”之后。

### 6.2 个人任务开启共享

1. 用户在个人任务中选择“开启共享”，预览将共享的目标、历史、上下文、结论与证据、材料和产物。
2. 模型凭据、私人偏好、本地草稿、无扰接手问答及未选择内容默认不共享。
3. 用户设置成员、角色和审批规则后完成转换，被选中记录保留时间和作者。
4. 转换后新产生的指令、工具活动和产物默认属于共享工作间，界面持续显示共享状态。
5. 已共享内容不能通过“撤销共享”伪装成从未被他人访问。

### 6.3 共享协作主流程

**创建工作间或从个人任务开启共享 → 定义目标与完成标准 → 选择 Runner → 邀请成员 → 维护共享上下文 → 开始 Agent 任务 → 多人观察与贡献 → 必要时审批或无扰接手 → 核对关键结论与活证据 → 确认结果与产物 → 归档／导出。**

默认仍为单 Runner 工作间。启用 Federated Beta 后，额外流程为：

**管理员允许团队 Beta → 负责人开启工作间 Beta → 节点所有者配对节点 → 所有者选择资源并批准 Grant → Agent 按节点执行获批步骤 → 按需审批模型外发／跨域传播 → 形成节点 Artifact 或 Patch → 所有者撤销或 Grant 到期。**

### 6.4 共享任务开始前

工作间负责人至少需要完成：

1. 填写工作间名称、任务目标和可判断的完成标准；
2. 选择一个可用 Runner；
3. 指定至少一名操作者和一名高风险动作审批人；
4. 确认工作间默认可见范围。

这些团队配置要求不适用于纯个人任务。若开启 Beta，还需确认支持的节点与资源类型；节点配对本身不共享资源，具体资源由所有者另行批准。

### 6.5 任务进行中

- 当前操作者可以开始、纠偏、排队和停止；其他成员按权限讨论、贡献和提出建议。
- 同一工作间一个活动任务；个人任务可并存并受资源配额约束。
- 所有成员通过各自 GUI 查看其有权看到的状态、输出、审批和产物。
- 被邀请接手者可先无扰准备，交接不自动停止任务或扩大数据权限。
- 联邦任务默认读取快照，固定工具按 Grant 执行；跨节点处理通过明确 Artifact，不制造统一文件系统。
- 模型外发、公共可见和跨域传播分别判断，来源内容中的指令不能提升权限。
- 修改贡献者文件默认生成 Patch，由所有者预览并在本地应用。
- 节点离线、拒绝、撤销或结果未知时明确显示，不自动重放副作用或伪装成功。

### 6.6 任务结束后

- 当前操作者或负责人确认完成、部分完成、失败或取消。
- 完成前检查关键结论证据，以及来源版本、节点、Grant、待复核和不可访问状态。
- 展示任务摘要、审批、产物、Patch、遗留待办和活动 Grant；未结束授权按规则到期或撤销。
- 个人任务保留在个人历史；共享工作间归档后只读。
- 档案和导出遵守资源可见范围；撤销不伪造历史从未读取，删除不承诺召回所有副本。

## 7. 详细功能需求

### GA-01：可独立使用的通用 Agent 能力（P0，产品底座）

**用户需求：** 用户希望先把 Unspool 当作日常通用 Agent 工具，而不是只有在团队协作时才有价值的前端。

**功能与业务规则：**

1. 用户无需创建团队、配置共享成员或邀请他人，即可创建个人任务。
2. 用户可在自己有权限的 Runner 上选择已配置模型与推理选项；模型凭据默认属于个人或管理员配置，不因开启共享而暴露。
3. 支持连续多轮任务、运行中纠偏、后续排队、停止和历史继续，保持与共享任务一致的基本操作语义。
4. Agent 可在授权范围内调用文件、命令及其他已配置工具；高风险动作仍遵守审批要求。
5. 支持添加参考材料、查看工作文件、保存和下载任务产物。
6. 支持个人任务历史的保存、搜索、置顶、归档和重新打开；关闭 GUI 不应无提示删除任务记录。
7. 多个个人任务可以并存，用户在任务之间切换时保留各自状态；可同时执行的数量由 Runner 资源和用户设置决定。
8. 个人指令、私人偏好和草稿默认不进入共享上下文，开启共享时必须由用户主动选择。
9. 个人任务可使用关键结论与活证据；转为共享时由用户决定是否共享这些记录。
10. 个人模式不被做成共享模式的只读演示，用户能够真正完成包含工具与产物的任务。

**验收要点：**

- 新用户不创建团队、不邀请成员，即可完成一个包含工具调用和产物保存的真实任务。
- 关闭并重新打开 GUI 后，能够找到并继续历史个人任务。
- 开启共享前后，模型凭据、私人偏好和未选择内容不会出现在其他成员视图中。

### GA-02：每用户独立 GUI 客户端（P0）

**用户需求：** 用户需要完整图形界面来管理 Agent 工作，而不是依赖终端命令或多人共用一个屏幕。

**功能与业务规则：**

1. 每名用户使用独立 GUI 和独立身份，既可处理个人任务，也可加入共享工作间。
2. GUI 至少提供任务／工作间导航、主对话与执行时间线、输入区、工具与审批状态、文件与产物面板、结论与证据、成员与操作权、Runner 状态和设置。
3. 个人与共享模式尽量复用一致的任务界面，通过清晰的共享标识和成员区域区分，而不是做成两套割裂产品。
4. 用户不打开终端，也应能完成新建任务、模型选择、工具审批、文件查看、历史恢复、开启共享、交接和归档。
5. 支持常见文本、Markdown、代码、差异和图像内容的合理展示；长输出可折叠、搜索和定位。
6. 支持调整面板、合理的信息密度、键盘操作、深浅色主题和清晰焦点状态。
7. 多名用户同时在线时，各自保留个人草稿、滚动位置和显示偏好，共享关键任务状态。
8. GUI 明确显示 Runner 连接、任务是否最新、共享状态、当前操作者及待处理风险。
9. 联邦 Beta 提供“我的环境”、Grant 审批、活动暴露、节点回执和跨域传播视图。

**UI 参考与独立性要求：**

- 可参考 [PI-Desktop](https://github.com/vastsa/PI-Desktop) 所体现的“项目／会话导航、持续对话主线、模型选择、工具过程、右侧工作面板”等通用交互思想。
- 不复制其源码、组件实现、样式、图标、插画、截图、文案、动画、品牌元素或具有识别性的视觉组合。
- Unspool 必须形成自己的信息层级、视觉语言、组件和商标，不能进行像素级复刻或以换色方式冒充原创。
- 设计评审需保留参考来源、差异说明和原创设计记录，具体合规要求见第 19 章。

**验收要点：**

- 目标用户仅使用 GUI 即可完成完整个人任务和共享协作流程。
- 两名用户各自使用 GUI 时，关键任务状态一致，本地草稿和显示设置互不影响。
- 发布前的设计来源审查未发现未获许可的 PI-Desktop 代码或资产复用。

### GA-03：本地／VPC Runner 的 Docker 部署运行（P0）

**用户需求：** 个人和团队需要在受控环境中运行 Agent，同时能够采用常见的 Docker 方式安装、升级和恢复，而不必依赖公共云执行服务。

**功能与业务规则：**

1. Runner 必须支持在本地或 VPC 中通过 Docker 部署运行，首个明确支持环境为受支持的 Linux Docker 主机。
2. 安装说明应使用户能够完成启动、停止、状态检查、数据备份和基本升级，不要求理解内部实现。
3. Runner 重启或容器更新后，个人任务、共享工作间、历史、设置和产物应按产品保留策略继续可用。
4. 用户可配置工作目录、模型访问、工具权限、网络访问和资源限制；敏感配置不出现在共享界面。
5. GUI 能显示 Runner 可用、繁忙、离线、升级中和异常状态，并说明对任务的影响。
6. 多个获授权的独立 GUI 可以连接同一 Runner，个人与共享任务仍遵守各自访问边界。
7. 升级前提示数据兼容性与备份要求；不能静默清空工作目录或历史记录。
8. MVP 不要求 Kubernetes 或公共云 Runner，也不能把 Docker 运行变成必须依赖 Unspool 云端中转才能使用。
9. 联邦 Beta 的贡献者节点可采用 Docker 分发，但不得把 Docker 等同于自动具备完整安全隔离。

**验收要点：**

- 在支持的干净 Linux Docker 主机上，新用户可依照文档启动 Runner 并完成个人 Agent 任务。
- 停止并重新启动 Runner 后，任务历史、工作文件和产物仍可访问。
- 两个获授权 GUI 可同时连接 Runner 并进入同一共享工作间。

### FR-01：团队与 Runner（P0）

**用户需求：** 管理员需要决定哪些成员可以使用产品，以及 Agent 可以在哪些受控环境中工作。

**功能与业务规则：**

1. 支持创建团队、邀请成员、停用成员和分配团队管理权限。
2. 管理员可登记本地／VPC Runner，并为其设置名称、用途说明、可用成员范围和默认安全策略。
3. 成员创建工作间时，只能看到自己有权使用的 Runner。
4. Runner 至少展示：可用、繁忙、离线、已停用。
5. 已停用 Runner 不能用于新工作间；已有工作间保留记录，不应被无提示删除。
6. Runner 不可用时，产品必须说明影响：无法开始新任务、进行中的任务可能中断，或仅部分工具不可用。
7. 团队管理员可允许 Federated Beta，但不能因此读取所有节点资源或替代所有者授权。

**验收要点：**

- 无权限成员不能通过链接或搜索发现受限 Runner。
- Runner 离线时，“开始任务”不可用，并展示可理解的原因。
- 停用团队成员后，其不能再操作或查看原本受限的内容；历史贡献仍保留署名。

### FR-02：工作间创建、配置与成员管理（P0）

**用户需求：** 负责人需要为一项持续工作建立统一空间，并明确目标和参与方式。

**创建工作间所需信息：**

| 字段 | 是否必填 | 规则 |
|---|---|---|
| 工作间名称 | 是 | 1～50 个字符，团队内可重名但需配合时间或负责人区分 |
| 任务目标 | 是 | 说明要解决什么问题，保存草稿后、开始任务前必须填写 |
| 完成标准 | 是 | 应尽量可判断，开始任务前必须填写 |
| Runner | 是 | 只能选择当前可用且本人有权使用的 Runner |
| Agent 配置 | 是 | 从团队允许的选项中选择，默认继承团队配置 |
| 初始成员 | 是 | 至少包含负责人；开始高风险任务前需满足审批人要求 |
| 可见范围 | 是 | MVP 默认仅受邀成员可见 |

**业务规则：**

1. 信息未填写完整时可以保存草稿，但不能开始任务。
2. 负责人可邀请成员并设置其角色和审批权限。
3. 任务执行中不能修改会改变当前任务含义的关键配置，例如 Runner 和 Agent 配置；如需修改，应先结束或停止当前任务。
4. 修改目标、完成标准、成员角色和关键配置时，所有成员都能看到变更记录。
5. 工作间支持归档，归档后不可新增讨论、指令、任务或产物，但保留查看和导出能力。
6. 默认共享模式为单 Runner；活动任务中不能静默切换 Runner 或联邦模式。

**验收要点：**

- 两名成员同时修改目标时，后提交者会被告知内容已变化，不会无提示覆盖。
- 新成员加入后能看到被邀请时已有的工作间记录；如产品决定限制历史可见，必须在邀请前明确提示。MVP 默认可见完整历史。

### FR-03：共享上下文（P0）

**用户需求：** 团队需要把对任务重要的事实、决定和约束放在一起，并明确哪些内容会影响 Agent。

**上下文类型：**

- 任务目标与完成标准；
- 已确认事实；
- 已作出决策；
- 约束与注意事项；
- 待办与阻塞；
- 参考材料与链接。

**功能与业务规则：**

1. 每条上下文包含标题、正文、作者、来源、更新时间和当前状态。
2. 每条上下文有明确的“提供给 Agent”状态，不能与“仅成员可见”混淆。
3. 负责人和当前操作者可维护全部共享上下文；协作者可新增并编辑本人提交的内容。
4. 协作者希望将本人内容提供给 Agent 时，由当前操作者确认后生效。
5. 修改和移除必须保留历史版本，不能无痕迹覆盖关键决策。
6. 任务进行中新增或修改的上下文，默认只影响下一任务；如需影响当前任务，操作者必须显式发送纠偏。
7. 每次任务都记录“本次 Agent 获得了哪些共享上下文”，历史任务不受后续修改影响。
8. 讨论、个人草稿和未被采纳的指令建议默认不提供给 Agent。
9. 受限节点结果进入共享上下文前必须满足来源许可，不能通过复制文本绕过。

**异常与边界：**

- 两人同时编辑同一内容时，需要提示版本冲突并由用户确认合并或覆盖。
- 被移除的上下文仍出现在历史任务记录中，但不再出现在后续任务的当前上下文中。
- 内容过长时提示用户整理和拆分，不应无提示截断后提供给 Agent。

**验收要点：**

- 用户能明确回答某条讨论是否会被 Agent 看到。
- 用户能查看任一历史任务开始时的上下文版本。
- 新加入成员可以通过共享上下文快速理解当前目标和关键决定。

### FR-04：讨论、指令建议与 Agent 指令（P0）

**用户需求：** 产品必须避免“人说的话”和“人让 Agent 做的事”混在一起。

**三种输入模式：**

| 模式 | 目的 | 是否直接影响 Agent |
|---|---|---|
| 讨论 | 团队成员之间交流 | 否 |
| 指令建议 | 提议下一步让 Agent 做什么 | 采纳后才影响 |
| Agent 指令 | 开始、纠偏或追加 Agent 工作 | 是 |

**功能与业务规则：**

1. 输入区域必须始终清楚显示当前模式，切换模式时保留草稿。
2. 非当前操作者进入 Agent 指令模式时，应引导其改为“指令建议”，并说明原因。
3. 指令建议展示建议人、时间和引用材料；当前操作者可采纳、编辑后采纳或忽略。
4. 采纳后同时保留原建议人和实际操作者信息。
5. 讨论支持提及成员和引用上下文、任务或产物。
6. 已被 Agent 接收的指令不能无痕修改；后续变化以新指令或纠偏呈现。

**验收要点：**

- 发送讨论不会在 Agent 会话中产生新的任务指令。
- 用户不需要理解底层能力，也能看懂“纠偏”和“后续排队”的差别。
- 采纳他人的建议后，时间线能同时体现贡献者和操作者。

### FR-05：操作权与任务交接（P0）

**用户需求：** 多人需要协作，但同一时刻必须明确谁有权直接推动 Agent。

**功能与业务规则：**

1. 工作间创建者默认成为初始操作者，也可在创建时指定其他操作者。
2. 只有当前操作者可以直接开始、纠偏、排队或停止任务。
3. 其他具备操作者角色的成员可以申请操作权；当前操作者可主动交接。
4. 主动交接需要接收者确认，避免把责任交给不知情成员。
5. 交接时自动生成交接摘要，至少包含：
   - 当前目标与完成标准；
   - 当前任务状态；
   - 最近关键决策；
   - 已完成的主要工作；
   - 待审批动作；
   - 排队指令与遗留待办；
   - 最新产物与当前阻塞。
6. 交接不改变任务执行状态。任务正在运行时，默认继续运行。
7. 当前操作者离线超过 2 分钟后，其他操作者可申请接管；工作间负责人可立即强制接管，但必须填写理由。
8. 操作权切换后，原操作者立即失去直接操作权限，但仍保留其原有讨论和贡献权限。

**异常与边界：**

- 接收者拒绝交接时，原操作权不变，并向发起人反馈。
- 两人同时申请离线接管时，只能一人成功，另一人看到最新操作者信息。
- 操作者离线但任务仍在运行时，工作间必须同时显示“任务状态”和“操作者状态”，不能混为一谈。

**验收要点：**

- 接手者不需要重新创建会话或重新描述完整背景即可继续工作。
- 旧操作者离线重连后，不会误以为自己仍有操作权。
- 强制接管在记录中清晰可见，并包含原因。
- 联邦交接摘要列出活动 Grant、剩余期限和受限结果；只读任务级 Grant 可保留，高风险执行和 Patch 应用重新确认。

### FR-06：Agent 任务操作（P0）

**用户需求：** 操作者需要明确控制任务开始、进行中调整和停止，并理解每个动作的后果。

**支持的操作：**

| 操作 | 可用时机 | 用户预期 |
|---|---|---|
| 开始任务 | 当前无活动任务 | Agent 根据目标和指令开始工作 |
| 运行中纠偏 | 任务执行中 | 调整当前工作方向，不等于重新开始 |
| 后续排队 | 任务执行中 | 当前工作结束后继续处理，不立即打断 |
| 停止任务 | 任务执行中或等待审批时 | 尽快停止当前执行 |
| 处理排队指令 | 停止或异常后 | 用户决定保留、修改、删除或继续执行 |

**功能与业务规则：**

1. 同一工作间同一时间只能有一个活动任务。
2. 开始任务前展示本次使用的目标、完成标准、Runner 和共享上下文范围。
3. 任务执行中，用户必须显式选择纠偏或后续排队，产品不得替用户猜测。
4. 停止属于重要操作，需要二次确认；停止后保留已经产生的记录与产物。
5. 停止后，排队指令默认保留但不自动继续，避免意外启动后续工作。
6. 重复点击或网络重试不应导致同一任务被重复开始。
7. Agent 自称“完成”不等于业务验收完成；负责人或操作者需要确认结果。
8. 任务结果由用户标记为完成、部分完成或未完成，并可填写原因。

**异常与边界：**

- Runner 异常中断时，状态显示为“待人工确认”，不得直接展示为正常失败或成功。
- 如果无法确定某个动作是否已经生效，必须明确提示用户先检查实际状态，不得建议直接重复执行。
- 任务失败后保留错误说明、最近进展和可执行的下一步建议。
- 多节点步骤失败不能伪装成整体成功，无法确认的副作用进入待人工确认且不自动重放。

### FR-07：任务过程与状态可见（P0）

**用户需求：** 所有成员需要及时了解 Agent 正在做什么、是否阻塞、产生了什么结果。

**时间线至少展示：**

- 成员讨论与 Agent 指令；
- Agent 文本输出；
- 工具活动及其简要说明；
- 高风险动作及审批状态；
- 关键上下文和决策变化；
- 操作权交接；
- 产物新增或更新；
- 任务开始、完成、失败、取消和异常中断。

**状态要求：**

1. 明确区分执行中、等待审批、正在停止、已完成、已失败、已取消和待人工确认。
2. 长时间没有新输出时展示最近更新时间和当前状态，不让用户误以为客户端卡死。
3. 工具活动可折叠，但高风险动作、失败和待审批项不能被默认隐藏。
4. 断线时明确显示“当前内容可能不是最新”，恢复后自动更新并提示同步结果。
5. 新成员可切换“任务概览”和“完整时间线”，避免被迫逐条阅读全部历史。
6. 支持按成员、任务、内容类型和时间筛选。
7. 任务概览展示本次 token 与费用信息；仅在上游提供可靠数据时展示具体数值，否则明确标记为暂不可得。跨任务汇总统计属于 P1。

**验收要点：**

- 五名成员同时查看时，看到的关键任务状态一致。
- 成员离线一段时间后重新进入，可以理解离线期间发生的主要变化。
- 仅查看不会使该成员被统计为有效协作者。
- 联邦模式按资源许可展示原文、摘要、哈希、受控状态或完全不显示；错误详情不得泄露受限参数。

### FR-08：高风险动作审批（P0）

**用户需求：** 团队需要在副作用发生前进行授权，而不是事后只看日志。

**默认高风险范围：**

- 修改、覆盖或删除文件；
- 执行可能改变环境或外部系统状态的命令；
- 向外发送内容或触发外部操作；
- 被管理员标记为高风险的其他工具动作。

**审批内容：**

1. 发起人及关联任务；
2. Agent 希望执行的动作及理由；
3. 影响对象和范围；
4. 完整、可读的操作内容；
5. 风险说明和审批有效期。

**业务规则：**

1. 被判定为高风险的动作，在批准前不得生效。
2. 审批人可以批准或拒绝，并可填写理由。
3. 批准只对本次提交的内容有效；内容或影响范围发生变化后必须重新审批。
4. 默认审批有效期为 15 分钟，超时未处理视为本次未获批准，并向 Agent 和操作者反馈。
5. 高风险动作默认不允许当前操作者自我审批；单人试用场景如需开放，必须由管理员显式允许并保留醒目记录。
6. 审批人离线、审批页面关闭或网络异常都不能被解释为批准。
7. 被拒绝的动作需要明确展示拒绝人和原因，Agent 可据此调整方案。
8. 所有审批结果进入任务记录和工作间档案。
9. 联邦模式将资源访问、模型外发、跨域传播、工具执行和 Patch 应用分别配置审批，上层审批不能替代资源所有者。

**验收要点：**

- 审批人能在不阅读整段会话的情况下理解自己正在批准什么。
- 修改操作内容后，旧批准不能继续使用。
- 超时、拒绝和异常都有明确且不同的界面状态。

### FR-09：参考材料与任务产物（P0）

**用户需求：** 团队需要在同一工作间共享任务输入和输出，并知道每个文件从哪里来。

**功能与业务规则：**

1. 成员可上传参考材料，默认单文件不超过 20MB，团队管理员可调整限制。
2. 支持常见文本和图片预览，其他格式提供文件信息与下载。
3. 每个文件展示名称、大小、上传或生成者、时间、关联任务及来源说明。
4. 明确区分“成员上传的参考材料”和“Agent 生成的任务产物”。
5. 文件可更新版本，历史任务仍能看到当时使用的版本。
6. 上传可执行文件只作为文件保存，不因上传或预览自动运行。
7. MVP 中工作间内文件默认对所有成员可见，不支持单文件单独授权。
8. 产物下载和完整档案导出需要相应权限。
9. 节点 Artifact 保留来源节点、所有者、快照、Grant、传播范围和版本，后续分享仍受原策略约束。

**异常与边界：**

- 文件过大、格式不支持预览或上传中断时，给出明确原因和重试方式。
- 来源无法确认的文件标记为“来源待确认”，不能冒充 Agent 产物。
- 文件内容可能包含敏感信息，上传和导出前应提醒用户工作间可见范围。

### FR-10：任务档案、搜索与导出（P0）

**用户需求：** 任务结束后，团队仍能复盘过程、查找决策并将结果交给未参与的人。

**功能与业务规则：**

1. 工作间档案包含基本信息、目标与完成标准、共享上下文历史、关键结论与活证据、讨论与指令、任务记录、审批记录、产物清单和成员贡献。
2. 支持按关键词、成员、任务和时间搜索。
3. 默认仅负责人可导出完整档案；其他成员是否可导出由工作间设置决定。
4. 导出内容使用通用可读格式，并要求产物清单与实际文件可以相互对应。
5. 对缺失文件、截断内容和无法确认结果的动作进行显著标注，不得静默省略。
6. 导出行为本身需要记录，包括导出人、时间和范围。
7. 联邦档案包含 Grant、快照、执行回执和传播记录；导出遵守资源范围并标注不可访问、撤销和记录不完整。

**验收要点：**

- 未参与任务的成员仅通过档案即可理解任务目标、关键决定、最终结果和遗留问题。
- 导出后不依赖本产品界面也能阅读主要记录。
- 归档不会删除历史贡献者的署名。

### FR-11：提醒与统计（P1）

**提醒范围：**

- 等待我审批；
- 有人请求与我交接；
- 我被提及；
- 我参与的任务完成、失败或等待人工确认。

**统计范围：**

- 工作间任务数、完成率和平均耗时；
- 有效协作成员数、交接次数、建议采纳次数；
- 高风险动作审批次数、拒绝次数和平均等待时间；
- token 与成本信息（仅在上游提供可靠数据时展示）。

统计用于理解协作效率，不用于给成员简单排名，也不将消息数量等同于贡献价值。

### FR-12：活证据——结论依据、有效状态与失效影响（P0，核心卖点）

**用户需求：** 团队不仅需要知道 Agent 曾经得出什么结论，还需要知道该结论为什么可信、由谁确认、现在是否仍然有效，以及依据变化后哪些工作会受影响。

**商业价值：** 该功能把产品从“共享执行过程”提升为“共享可信结果”。对于复核成本高、错误代价大的团队，付费理由不是少看几条消息，而是减少错误决策、重复核查和交付后返工。销售演示应直接展示：一份来源失效后，系统如何找到受影响的决策、产物和完成判断。

**功能与业务规则：**

1. 用户可以将 Agent 输出、讨论或文件内容提炼为“关键结论”，类型包括事实、假设和决策。
2. Agent 可以建议关键结论和来源，但不能自行将其标记为“已确认”；确认必须由有权限的成员完成。
3. 每条关键结论至少展示：内容、类型、来源、提出人、确认人、确认时间、适用范围和当前有效状态。
4. 有效状态包括：未验证、已确认、待复核、已失效。产品不使用看似精确的模型置信分替代人工判断。
5. 已确认的关键结论原则上至少关联一项来源。来源可以是工作间内的工具结果、文件、产物、讨论或用户填写的引用。
6. 用户可为来源设置复核时间或有效期限；到期后进入待复核，而不是自动变为失效。
7. 用户可以建立关键结论与完成标准、后续决策、产物及待审批动作之间的关联。
8. 当工作间内已知来源被更新、替换、撤销或标记失效时，产品展示受影响清单，并将直接依赖项标记为待复核。
9. 失效影响提醒只表示“需要复核”，不自动推翻业务决策、删除产物或撤销已经发生的外部动作。
10. 外部来源若未接入自动监测，由成员手动发起复核或标记失效；产品不得假装已经检查其最新状态。
11. 任务标记“完成”前，展示关键结论的证据覆盖情况。存在缺证、失效或待复核项时，用户需要补齐依据、改为部分完成，或由负责人记录例外理由。
12. 工作间提供“当前结论与复核视图”，集中展示已确认结论、待复核项、缺失依据和最近失效影响。
13. 联邦证据记录节点、快照、Grant 与执行版本；不可访问、所有者撤销和内容失效是不同状态。

**异常与边界：**

- 有来源不代表来源真实或结论正确；界面必须避免使用“系统已证明为真”等过度承诺。
- 多项结论引用同一来源时，只提醒一次来源变化，同时分别展示各自影响。
- 来源之间存在冲突时，标记为待复核并呈现冲突，不自动选择看起来更新或更合理的一方。
- 负责人可以例外完成，但不能消除缺证记录，后续查看者仍能看到例外原因。

**验收要点：**

- 更新一个被多项结论引用的工作间来源后，用户能看到全部已知受影响项。
- 一个缺少有效证据的关键结论不能被无提示地当作“已确认”。
- 复核完成后，结论可以重新确认，并保留此前失效与复核历史。

### FR-13：无扰接手——接手前私人的只读准备（P0，核心卖点）

**用户需求：** 接收者看完交接摘要后仍有疑问时，不应只能打断原操作者、在公共时间线提出基础问题，或在尚未理解任务时先接受操作权。

**商业价值：** 该功能直接优化本产品最核心的交接时刻，能够减少同步会、重复解释和错误接手，使跨班次、跨时区及专家临时参与更容易。它也能形成明确演示：原任务持续运行，接收者同时私下完成背景问答，随后带着已经核实的下一步接手。

**功能与业务规则：**

1. 收到交接邀请的接收者可以先选择“准备接手”，不必立即接受或拒绝。
2. 准备期间展示交接摘要，以及按接收者角色组织的背景视图：目标、当前状态、关键决策、有效证据、待审批项、阻塞、产物和建议下一步。
3. 接收者可以就工作间已有记录进行私人问答，例如“为什么采用这个方案”“哪个结论尚未验证”“如果我只想先控制风险，应先做什么”。
4. 涉及背景事实的回答必须关联可查看的来源；只能提供推测时必须显著标记，已有记录不足时明确说不知道或不确定，不能编造完整背景。
5. 准备模式为只读：不能开始、纠偏、排队或停止任务，不能审批，不能执行真实工具或改变文件与外部系统。
6. 私人问答默认仅接收者可见，不进入公共时间线，也不自动提供给正在执行任务的 Agent。
7. 当前任务继续运行。准备期间如果目标、操作者、关键决策、风险或阻塞发生实质变化，接收者会收到“背景已变化”提醒，并可更新准备视图。
8. 接收者可将问答中的内容整理为“待发布澄清”，经本人确认后发布为讨论、共享上下文或交接说明；发布前仍可编辑。
9. 发布关键结论时仍需遵守活证据规则，私人问答中的 Agent 回答不会自动成为已确认事实。
10. 接收者准备后可接受或拒绝交接。接受时才获得操作权；拒绝或退出准备模式不影响原操作者和任务。
11. 接收者可以保留一份“仍未解决的问题”清单，选择私下保留或公开给原操作者。
12. 产品分析默认只记录准备时长、问答次数、是否发布澄清和是否接受交接，不采集私人问题正文。
13. 联邦模式下只能使用接收者本人有权访问的来源，不能借用原操作者或其他成员权限回答。

**异常与边界：**

- 无扰接手是背景理解与核对工具，不是完整任务沙盒，也不承诺可以预演真实执行结果。
- 如果问答需要超出接收者权限的信息，应拒绝回答并说明权限边界。
- 背景持续变化时，回答必须对应明确的记录时间，避免把旧摘要当作最新状态。
- 私人问答可以存在错误，接收者发布前必须人工确认；关键结论还需完成证据确认。

**验收要点：**

- 接收者完成多次私人问答时，公共时间线没有新增这些内容，当前任务也没有被暂停或修改。
- 接收者能从回答跳转到可核对的来源，并能把选中的澄清发布到工作间。
- 准备期间发生关键状态变化时，接收者会在接受操作权前看到提醒。

### FB-01：Beta 开关、范围与发布管理（P0）

**需求：**

1. 新团队和既有团队默认关闭联邦能力，不能因版本升级自动开启。
2. 团队、工作间和节点三级启用缺一不可；具体资源仍需单独 Grant。
3. 开启时展示支持平台、资源类型、已知限制、数据处理路径和安全边界，不使用笼统的“我已知悉风险”替代具体说明。
4. 团队可配置允许加入的节点所有者、资源类型、最大权限和默认期限。
5. 工作间可选择仅快照、快照＋固定工具或快照＋固定工具＋Patch 建议，不能越级开放。
6. 关闭 Beta 后不影响 Stable 个人任务、单 Runner 工作间和历史档案。
7. Beta 功能变更不得静默扩大既有 Grant；需要新增能力时重新征得所有者同意。
8. 产品提供 Beta 版本标识、反馈入口、安全公告和已知问题说明。
9. 商业页面必须清楚区分 Stable 与 Beta，不把 Beta 能力计入未注明限制的正式承诺。

### FB-02：贡献者节点配对与所有权（P0）

**需求：**

1. 节点所有者通过独立 GUI 或受控安装流程连接本人本地／VPS 节点。
2. 配对至少确认用户身份、节点名称、设备归属、目标团队、支持状态和允许能力。
3. 新节点默认只有“已连接、未贡献资源”状态，配对不等于共享文件。
4. 节点状态包括待确认、在线、繁忙、离线、已暂停、已撤销、已隔离和不兼容。
5. 所有者可修改名称、查看最近活动、撤销节点和移除团队访问。
6. 节点撤销后不能继续请求新资源；历史回执保留。
7. 节点不得要求所有者开放公网入站端口或加入一个默认全网互通的私人网络。
8. 节点支持状态必须真实呈现；未经验证的桌面系统不能被标记为“安全贡献执行环境”。
9. 产品区分“设备已配对”“策略兼容”“安全状态未知”，不把配对成功等同于可信执行证明。
10. 失去设备或怀疑凭据泄漏时，所有者可以立即撤销该节点及其活动 Grant。

### FB-03：资源注册与暴露预览（P0）

**文件／目录资源：**

1. 所有者显式选择路径，默认不展示整个设备目录给远程方。
2. 授权预览展示文件数量、总大小、包含子目录、快照时间、目标接收方和有效期。
3. 路径逃逸、符号链接指向范围外、隐藏切换到上级目录等请求必须被拒绝。
4. 可提供常见凭据文件和敏感目录提醒，但允许范围必须由明确包含规则决定，不能依赖黑名单排除。
5. 文件路径、名称和目录结构本身的可见性单独配置。
6. 所有者未选择的新增目录不因父级操作而被隐式加入。

**固定工具资源：**

1. 工具以所有者理解的名称和用途出现，例如“运行项目测试”“查询最近一小时脱敏日志”。
2. 明确可配置参数、允许值、工作目录、网络需要、超时、输出范围和风险级别。
3. 未声明的参数、额外命令串联和环境变量继承默认不允许。
4. 所有者可以只允许特定参数组合或每次执行都审批。
5. 工具说明必须真实反映可能副作用，不得把任意命令包装成“只读工具”。

### FB-04：Grant 请求、批准与生命周期（P0）

**需求：**

1. Agent 或成员发起请求时必须说明任务目的、资源、操作、接收方和期限。
2. 所有者可以批准一次、批准到任务结束、批准固定时长、缩短范围或拒绝。
3. 默认选择最短可行期限和只读权限，不提供“记住并永久允许”作为默认选项。
4. 高风险操作可要求额外审批人，但额外审批不能替代所有者。
5. 资源、参数、目的、操作者权限需求、模型接收方或传播目标发生实质变化时重新授权。
6. 授权默认不可转让、不可转发、不可由 Agent 自行拆分扩大。
7. 节点对所有访问请求重新检查当前 Grant，即使请求来自已知服务器也不例外。
8. 节点本地策略比团队默认更严格时，以更严格者为准。
9. 所有者可以看到活动、即将到期、已撤销和历史 Grant。
10. 授权与拒绝都产生回执，包括原因、时间、操作者和影响任务。

### FB-05：文件快照与只读访问（P0）

**需求：**

1. Agent 默认读取快照，而非在任务中无声跟随实时文件变化。
2. 快照记录来源节点、所有者、范围、版本、时间和内容校验信息。
3. 本地文件变化后提示“来源已变化”，由所有者决定是否提供新快照；不自动更新已授权内容。
4. 快照是否缓存在协调环境、缓存多久、哪些成员可访问必须明确。
5. 未批准中央缓存时，节点离线后不能假装仍可读取完整快照。
6. 大文件、二进制文件和超预算目录提供明确限制与处理选项。
7. 读取结果按 Grant 决定仅供 Agent、指定成员、公共摘要或 Artifact。
8. 不把不同节点目录拼接为一个透明统一文件系统；跨节点处理通过明确 Artifact。
9. 文件删除或所有者撤销影响未来访问，不伪造历史上从未读取。

### FB-06：受控工具执行（P0）

**需求：**

1. Beta 首期只允许已注册固定工具模板，任意 Shell 请求必须拒绝。
2. 每次执行绑定任务、节点、工具、参数、Grant、资源预算和结果接收方。
3. 工作目录、可执行操作、环境变量、网络目标和输出范围受所有者策略限制。
4. 默认不继承节点全部凭据、环境变量、文件系统和网络能力。
5. 每次执行使用干净且边界明确的运行上下文，避免上一次任务残留影响下一次。
6. 所有者可以设置每次执行审批、资源上限、超时和是否允许网络。
7. 执行过程显示等待、运行、取消、成功、失败、超时和结果未知。
8. 节点异常中断时，可能产生副作用的执行进入结果未知，不自动重放。
9. 工具输出先按来源域策略处理，不默认广播给所有工作间成员。
10. 产品展示“执行完成”不代表结果真实或业务结论正确；恶意或受损节点仍可能返回不可信结果。

### FB-07：Patch 与本地应用（P0）

**需求：**

1. Agent 对贡献者文件的修改默认生成 Patch，不直接写回。
2. Patch 绑定来源节点、快照版本、目的和关联任务。
3. 所有者查看文件差异、影响范围、相关证据和可能风险。
4. 来源文件已变化时提示版本冲突，不能盲目覆盖。
5. 应用 Patch 是独立权限和审批，不因读取或生成 Patch 自动获得。
6. 应用由所有者或明确获授权者在本地确认，结果生成新版本与证据。
7. 拒绝 Patch 不影响原始只读 Grant，除非所有者主动撤销。
8. 已应用的外部副作用不能通过删除时间线记录来撤销。

### FB-08：跨域数据流、模型外发与可见性（P0，安全核心）

**需求：**

1. 每项节点数据和派生 Artifact 保留来源节点、所有者、许可和默认敏感级别。
2. 数据从 A 域进入 B 域前，检查该传播是否被原 Grant 允许。
3. 原始内容发送给外部模型前，单独确认模型接收方、内容范围、目的和保留策略。
4. 数据进入公共时间线或长期组织记忆也属于新的可见性决定。
5. 派生结果默认继承最严格来源限制，只有有权限所有者复核后才能降低级别。
6. 跨节点传输展示来源、目的、内容类型、数量、接收方和任务原因。
7. 高敏感受控策略下支持来源所有者与目标域所有者双方批准，或额外安全审批。
8. 脱敏和秘密检测是辅助能力，不能替代权限，也不能承诺识别所有敏感信息。
9. 模型、工具或用户不得通过摘要、错误信息、日志、文件名或代码注释绕过传播限制。
10. 分析埋点不采集资源正文、参数、路径、模型外发内容和私人问答。
11. 无权限成员看到的结果需要避免泄露敏感参数；必要时完全不显示该步骤。
12. 任何被拒绝的传播都必须留下可审计原因，并允许 Agent 在权限内提出替代方案。

### FB-09：多节点任务协调与交接（P0）

**需求：**

1. 任务计划展示各节点步骤、依赖、当前状态、Grant 和预计阻塞。
2. 各节点只处理自身获批步骤，协调方不能把本地拒绝解释为自动改派到其他私密资源。
3. 无依赖步骤可继续，有依赖步骤明确等待或失败，不伪装整体成功。
4. 节点重试遵循工具副作用与 Grant 次数限制，结果未知时先人工确认。
5. 当前操作者交接时，接收者看到活动 Grant、剩余时间、受限结果和节点状态。
6. 只读任务级 Grant 可保留到原期限；高风险执行与 Patch 应用重新确认。
7. 接收者不因接受操作权自动获得原操作者个人可见数据。
8. 资源所有者可因操作者变化暂停或撤销 Grant。
9. 外部专家到期退出后，其个人访问终止，但已授权贡献和署名保留。

### FB-10：活动暴露指示与节点访问回执（P0）

**需求：**

1. 所有者在本地 GUI 持续看到节点是否正在被任务使用。
2. 活动视图展示当前工作间、任务、资源、操作、开始时间、请求方和数据接收方。
3. 提供停止新访问、暂停节点和隔离节点的明确动作。
4. 每次读取、执行、模型外发、跨域传播、Patch 生成／应用和拒绝均形成回执。
5. 回执至少包含任务、请求方、资源、操作、时间、结果、数据去向和关联 Grant。
6. 所有者可以按任务、时间、资源和结果筛选并导出本人节点回执。
7. 协调方和团队成员只看到自己有权查看的回执粒度，不能通过全局审计获得敏感参数。
8. 节点断线后本地回执可按产品策略补交，补交失败必须标记记录不完整。
9. 回执用于问责和复盘，不宣称能够证明未发生所有形式的侧信道泄漏。

### FB-11：资源预算与本地保护（P0）

**需求：**

1. 所有者可限制文件数量、总大小、单次读取、输出大小、执行时长和并发数。
2. 工具可设置计算、内存、网络和进程等预算；具体可配置项随支持平台公布。
3. 团队上限与节点本地上限同时存在时取更严格值。
4. 预算耗尽后停止或拒绝新工作，不自动申请更高额度。
5. 超时、输出过大和异常资源消耗需要明确通知所有者和当前操作者。
6. 节点所有者可以设置本地免打扰时段或只允许手动批准，但产品应说明其对任务连续性的影响。
7. 资源不足不能成为临时关闭安全策略或扩大挂载范围的理由。

### FB-12：离线、撤销、隔离与事件处理（P0）

**需求：**

1. 节点离线时，相关步骤显示离线及最后已知状态，不伪造成功。
2. 是否可使用已缓存快照取决于原 Grant；未获缓存许可则停止访问。
3. 撤销 Grant 后立即阻止新访问，进行中的操作按可取消性安全停止或标记待确认。
4. 节点暂停用于临时停止新工作；隔离用于安全事件，默认要求人工检查后恢复。
5. 节点所有者隔离节点不需要工作间负责人同意。
6. 协调方发现异常请求时可暂停任务，但不能单方解除节点本地隔离。
7. 结果未知的外部副作用需要用户检查真实环境后再决定重试。
8. 安全事件保留相关 Grant、回执、版本和任务关系，支持限定范围导出。
9. 节点数据删除、回执保留和审计元数据保留分别呈现，不以“删除全部”作出无法兑现的承诺。
10. Beta 全局停用、工作间停用和节点停用均执行一致的新访问阻断规则。

### 8.2 全局业务约束

1. 团队管理员不因为管理身份自动获得所有工作间内容访问权。
2. 一个工作间同一时间只有一名当前操作者和一个活动任务。
3. 讨论、指令建议和直接指令必须始终可区分。
4. 高风险动作默认需要独立于当前操作者的审批。
5. 工作间成员默认看到相同的共享上下文和工具结果；需要不同保密级别的任务应拆分工作间。
6. 离线、关闭页面或网络异常都不等于授权、批准或任务完成。
7. 已产生的历史记录不能因成员退出、角色变化或工作间归档而失去署名。
8. 有来源不等于结论为真，确认、复核和例外完成都必须保留人员与时间。
9. 无扰接手中的私人问答默认不公开、不影响主任务，也不能绕过任何现有权限。

### 8.4 联邦安全不变量

1. 默认拒绝，明确允许才可访问。
2. 最终资源授权必须在节点本地可验证，服务器声明不能替代。
3. 节点不因配对、加入团队或进入工作间获得资源共享义务。
4. 不允许通过路径、链接、工具参数、错误输出或派生 Artifact 绕过范围。
5. 不继承用户全部环境、凭据、网络和文件权限。
6. Grant 默认短期、只读、不可转发、不可升级。
7. 资源、操作、目的和接收方变化需要重新判断授权。
8. 来自内容的指令不能改变权限策略。
9. 模型外发、成员可见和跨域传播分别判断。
10. 派生结果默认继承最严格来源限制。
11. 高风险操作可要求多人审批，但任何审批人不能替代资源所有者。
12. 撤销立即停止新访问，结果未知时不自动重放。
13. 节点所有者始终可以暂停、撤销和隔离本人节点。
14. 团队管理员和工作间负责人不能解除节点本地拒绝或隔离。
15. 日志、分析和错误提示不能成为绕过数据可见性的旁路。
16. 撤销、删除和导出必须如实说明历史副本与审计元数据边界。

### 8.5 跨节点提示词注入规则

若 A 节点内容要求 Agent 读取 B 节点、向外部模型发送内容或写入 C 节点，产品必须把它视为新的权限请求，而非原任务的自然延伸。

默认行为：

1. 不因 A、B、C 都在同一工作间而放行；
2. 检查原始目的和各域 Grant；
3. 需要时向资源所有者和接收方展示新的审批；
4. 被拒绝后保留原因，不允许换工具、换摘要或换错误通道重试同一越权目标；
5. 相关结论标记可能受到不可信内容影响，进入待复核。

## 9. 页面与交互需求

### 9.1 信息架构

MVP 至少包含以下一级视图：

1. **任务首页**：个人任务、共享工作间、我负责的、等待我处理和已归档。
2. **工作间概览**：目标、完成标准、当前状态、当前操作者、关键上下文、最近进展和产物。
3. **协作时间线**：讨论、指令、Agent 输出、工具活动、审批、交接和系统状态。
4. **共享上下文**：按事实、决策、约束、待办和参考材料分类管理。
5. **成员与操作权**：成员角色、在线状态、当前操作者、交接申请。
6. **审批中心**：待我审批、已处理、已超时及关联任务。
7. **材料与产物**：参考材料、生成产物、版本和来源。
8. **任务档案与导出**：历史任务筛选、结果确认、归档和导出。
9. **工作间设置**：Runner、Agent 配置、可见范围、审批规则和提醒设置。
10. **结论与证据**：关键结论、来源、有效状态、失效影响和复核记录。
11. **接手准备**：私人只读问答、背景变化提醒、待发布澄清和接受／拒绝交接。
12. **个人设置与 Runner 管理**：模型与凭据、个人偏好、Runner 连接、Docker 运行状态、数据和备份。

### 9.2 个人任务与工作间列表

**展示内容：** 名称、个人／共享类型、目标摘要、负责人、当前操作者、当前任务状态、最近更新时间和未读事项。

**筛选：** 我的个人任务、共享工作间、我负责的、我可操作的、等待我审批、等待我接管、执行中和已归档。

**空状态：** 首次进入时提供“新建个人任务”“创建共享工作间”和“查看示例任务”入口，不强迫用户先建立团队。

### 9.3 工作间概览

这是新成员和接手者的默认入口，应优先回答：

- 这项工作要解决什么问题？
- 怎样算完成？
- 现在进行到哪里？
- 谁在操作？
- 最近有哪些关键决定？
- 当前是否等待审批或人工确认？
- 下一步和阻塞是什么？
- 最新产物在哪里？

“查看完整过程”作为二级动作，避免完整时间线淹没关键状态。

### 9.4 协作时间线与输入区

- 人员讨论、Agent 指令、Agent 输出和系统状态应有明显视觉差异。
- 输入区始终标明当前模式，并提供简短的后果说明。
- 非当前操作者尝试直接操作 Agent 时，不直接报错终止，而是提供“转为指令建议”。
- 审批、交接和异常状态需要在时间线与独立视图中同时可见。
- 长输出支持折叠、搜索和跳转；高风险与失败信息默认突出。
- 用户离开期间的新内容需要数量提示和一键定位。

### 9.5 交接确认页

接收者在确认前至少看到交接摘要和当前风险。确认按钮文案应体现责任，例如“接受操作权并继续任务”，而非笼统的“确定”。

若任务正在执行，需要单独提示：“接受操作权不会自动停止或重新启动当前任务。”

### 9.6 审批详情页

审批人首先看到动作、影响范围、发起人和风险，再查看关联上下文。批准和拒绝不能只用颜色区分；拒绝时应鼓励填写可供 Agent 调整方案的理由。

内容在审批期间发生变化时，页面应立即提示“原审批内容已失效”，不能继续显示可批准状态。

### 9.7 通用反馈与异常状态

所有页面需要设计以下状态：

- 首次使用空状态；
- 正常加载与长时间加载；
- 无权限；
- 内容已被其他成员更新；
- 当前操作者已变化；
- Runner 离线；
- 客户端断线与恢复同步；
- 任务等待审批或人工确认；
- 文件上传失败或不可预览；
- 工作间已归档。

任何异常提示都应包含“发生了什么、是否影响任务、用户现在可以做什么”。

### 9.8 活证据与结论复核页

默认优先展示“待复核”和“缺失依据”，而不是罗列所有历史来源。每条关键结论都应能展开查看来源、确认历史、适用范围和受影响对象。

失效影响页按“需要复核的结论—受影响的完成标准／产物／后续动作”组织，不提供一键自动全部推翻。重新确认前，用户需要说明复核结论，必要时补充新来源。

### 9.9 无扰接手准备页

页面顶部持续显示“私人只读准备，不会影响主任务”，并标明背景记录时间。问答区与交接摘要并列，接收者可以核对来源、收藏澄清和标记未解决问题。

接受操作权前，页面再次汇总：已核实的背景、仍未解决的问题、准备期间发生的变化和即将承担的控制权限。退出准备模式时明确提示哪些私人内容会被保留、哪些会被删除，不使用含糊的“完成”按钮。

### 9.10 个人任务开启共享界面

开启共享前使用内容预览，而不是只弹出成员邀请框。用户按“目标与历史、上下文、结论与证据、参考材料、产物”选择共享范围，并明确看到默认排除的私人内容。

转换完成后，界面持续显示“已共享”和可见成员范围。用户能够回到个人历史，但不能通过切换按钮误以为已被他人查看的内容会因此消失。

### 9.11 我的环境与活动暴露

所有者可以查看本人节点、资源、活动 Grant、当前使用任务、数据去向和最近回执，并执行暂停、撤销和隔离。活动暴露持续可见，不能只显示一次通知后消失。

### 9.12 Grant 请求与批准页

首屏展示目的、资源、操作、接收方和期限。读取、模型外发和公共可见拆项呈现，批准按钮体现具体后果，例如“允许本次任务读取此快照 30 分钟”。

### 9.13 跨域传播审批页

以“来源 → 接收方”展示原文、摘要、Artifact 或 Patch 的流向，说明派生结果为何继承限制。无权成员的错误提示不得泄露受限路径和参数。

## 10. 数据统计与埋点需求

### 10.1 统计原则

- 用于回答产品问题，而不是为了收集而收集。
- 默认采集行为元数据，不采集指令正文、讨论内容、工具参数和文件内容。
- 产品分析与安全审计分开管理；分析数据不能替代责任记录。
- 所有核心指标必须有明确触发条件，避免依赖人工解释。

### 10.2 核心埋点

| 事件 | 触发时机 | 关键属性 | 要回答的问题 |
|---|---|---|---|
| 新建个人任务 | 用户首次创建非共享 Agent 任务 | Runner 类型、是否首次使用、入口 | 通用 Agent 底座是否真正可用 |
| 完成个人任务 | 用户确认个人任务结果 | 首次任务耗时、工具与产物使用情况、结果类型 | 个人用户是否获得独立价值 |
| Docker Runner 就绪 | 用户完成 Docker Runner 启动并可开始任务 | 部署环境、配置耗时、失败原因类别 | 安装部署是否成为采用门槛 |
| 个人任务开启共享 | 用户完成选择性共享转换 | 共享内容类别、邀请成员数、距个人任务创建时间 | 个人使用是否自然转化为协作 |
| 创建工作间 | 草稿首次创建成功 | 团队、创建者、Runner 类型 | 用户是否开始尝试产品 |
| 完成工作间配置 | 首次满足开始任务条件 | 配置耗时、初始成员数 | 创建门槛是否过高 |
| 邀请第二名成员 | 第二名成员接受邀请 | 距创建时间 | 单人工具是否转化为协作工具 |
| 开始首个任务 | 工作间首次开始 Agent 任务 | 配置耗时、成员数 | 用户是否到达核心价值 |
| 任务完成 | 用户确认任务结果 | 耗时、结果类型、参与人数 | 任务是否真正完成 |
| 有效协作发生 | 第二名成员首次产生有效行为 | 行为类型、距创建时间 | 多人协作是否真实发生 |
| 指令建议被采纳 | 建议被操作者采纳 | 建议人与操作者关系、等待时长 | 非操作者贡献是否有价值 |
| 操作权交接完成 | 接收者确认接管 | 交接耗时、任务是否运行中 | 共享工作是否支持接力 |
| 高风险审批完成 | 批准、拒绝或超时 | 结果、等待时长、动作类别 | 审批是否成为阻塞 |
| 关键结论确认 | 有权限成员确认结论 | 结论类型、来源数量、确认耗时 | 团队是否愿意维护可信结果 |
| 失效影响产生 | 来源变化导致结论待复核 | 受影响结论与产物数量、发现时点 | 活证据能否提前发现返工风险 |
| 无扰接手开始 | 接收者进入准备模式 | 任务是否运行中、交接类型 | 接收者是否需要独立准备 |
| 无扰接手完成 | 接受、拒绝或退出准备 | 准备时长、问答次数、发布澄清数、是否接受 | 是否减少追问并提高接手成功率 |
| 档案导出 | 完整档案导出成功 | 导出人类型、任务时间范围 | 工作记录是否具有复用价值 |
| 工作间再次活跃 | 非连续会话中再次开始任务 | 距上次活跃时间 | 工作间是否具备持续价值 |

### 10.3 指标口径

- **接手耗时：** 从接收者确认操作权，到其完成首次有效控制或上下文操作的时间；同时通过短问卷补充“恢复背景实际花费时间”，两种数据分开呈现。
- **有效协作者：** 至少产生一次有效协作行为的成员，不含只读和在线状态。
- **任务完成率：** 用户确认结果为“完成”的任务数／已结束任务数；技术执行成功不等于任务完成。
- **个人任务激活率：** 新建首个个人任务后，在同一使用会话或约定激活周期内完成任务的用户数／新建首个个人任务的用户数。
- **共享转化率：** 在一定观察周期内开启共享的个人任务数／全部个人任务数；同时观察共享后是否产生第二名有效协作者，避免只追求点击转换。
- **建议采纳率：** 被采纳或编辑后采纳的建议数／已提交建议数。
- **关键结论有效证据覆盖率：** 标记“完成”的任务中，具有已确认结论且其依赖来源未处于失效或待复核状态的关键结论数／全部关键结论数；负责人例外完成不计为有效覆盖。
- **无扰接手收益：** 对相同团队、相近任务类型的普通交接与无扰接手分别统计准备时长、向原操作者追问次数、接受后 24 小时内返工次数，不用单次个案推断整体收益。

### 10.4 Federated Beta 指标

**补充北极星：每周完成的真实多环境任务数。** 至少两名不同资源所有者的节点作出有效贡献，Grant 与回执完整，且任务到达用户确认结果，才计入。

| 维度 | 指标 |
|---|---|
| 激活 | Beta 开启 → 节点配对 → 首个 Grant → 首个多环境任务完成 |
| 环境接入效率 | 从邀请协作者到其环境首次可用的时间 |
| 授权体验 | 批准率、拒绝原因、批准耗时、缩权比例、过期和撤销 |
| 数据控制 | 模型外发审批、跨域阻断、派生结果降级和隔离 |
| 安全健康 | 超范围请求、路径逃逸阻断、异常重试、结果未知和回执缺口 |
| 商业留存 | Beta 团队次周／次月继续使用率与真实任务频率 |
| 支持成本 | 每团队节点、授权和兼容问题的人工支持时间 |

连接节点数、暴露文件数和远程命令数不能作为核心价值指标；分析不采集资源正文、路径、参数和私人问答。

### 10.5 商业继续／停止条件

继续投入联邦能力需要：至少 3／5 试点团队完成多个真实多环境任务；至少一半团队出现集中上传难以替代的价值；所有者能够独立配置 Grant；授权与支持成本没有吞噬节省时间；无未解决严重越权或数据流绕过。若长期没有复购或授权成本过高，应保留 Beta 或停止扩张。

## 11. 非功能需求

### 11.1 易用性

1. 新成员不阅读帮助文档，也应能区分讨论、建议和直接指令。
2. 当前任务状态、当前操作者和待处理风险始终容易找到。
3. 高风险操作不能只靠图标或颜色表达。
4. 长任务中常用操作可在少量步骤内完成，避免频繁切换视图。
5. 所有错误提示使用用户语言，不直接暴露内部错误或技术术语。

### 11.2 性能与并发体验

在团队正常网络与 Runner 可用的情况下：

- 打开常用工作间概览的时间目标为 3 秒以内；
- 用户执行普通操作后的界面反馈目标为 1 秒以内，不包含 Agent 实际工作耗时；
- Agent 新输出在正常网络下应及时呈现，目标延迟不超过 1 秒；
- 至少 5 个独立客户端同时查看同一工作间时，关键状态保持一致；
- 长历史工作间应支持分段加载，不因记录增多而无法打开。

### 11.3 可靠性与可恢复性

1. 已被产品确认接受的操作，不能因页面刷新或客户端重连而无提示丢失。
2. 重复点击、重试或恢复连接不能导致同一任务被重复启动。
3. 客户端离线不应自动停止正在执行的任务。
4. Runner 异常后，产品必须保存最后已知状态，并明确哪些内容需要人工确认。
5. 无法确认某个副作用是否发生时，不得将其展示为确定成功或确定失败。
6. 任务历史、审批和产物来源在归档后仍可查看。

### 11.4 安全与隐私

1. 所有工作间和 Runner 均按授权范围访问。
2. 高风险动作必须受审批规则约束，不能仅依靠界面隐藏来阻止。
3. 凭据和敏感配置不出现在共享讨论、任务时间线、审批记录或导出内容中。
4. 工作间内共享内容默认对所有成员可见，创建和邀请时必须明确提示。
5. 成员被停用或移出工作间后，不应继续获得新内容；其历史署名保留。
6. 导出属于敏感操作，必须有权限控制和记录。
7. 对可能包含敏感内容的文件上传、工具结果和完整导出提供风险提示。
8. 私人接手问答不能向原操作者或其他成员默认公开，产品分析不得采集其正文；接收者主动发布时才转为共享内容。
9. 对未接入持续监测的来源，必须展示最后确认时间，不能用“实时有效”“系统已验证”等措辞误导用户。

### 11.5 可维护的需求表达

- 每个功能需求必须能映射到至少一个用户目标和验收场景。
- 交互文案、角色名称和任务状态在各页面保持一致。
- PRD 变更需要更新修订记录，并通知设计、研发和测试。
- 技术方案不得悄悄改变本文定义的用户语义；如必须调整，应回到产品评审。

### 11.6 Federated Beta 安全、容量与运维

- 至少支持 5 个贡献者节点和 20 个活动 Grant／工作间的验收规模；慢节点不阻塞无依赖步骤。
- 节点跨地域和家用网络允许不同延迟，分别展示状态，不作统一 1 秒执行承诺。
- 节点离线是正常业务状态；已撤销、过期和预算耗尽的 Grant 在恢复后不能复活。
- 协调环境被攻破时，已集中数据和有效 Grant 可能受影响；节点应拒绝超范围请求，但不承诺零损失。
- 节点被攻破时可伪造本节点结果，其他节点只暴露已明确传输内容，不因同一工作间自动失守。
- 提供威胁模型、支持矩阵、Grant 与数据流、撤销隔离、事件处理和安全公告文档。
- GA 前完成独立威胁模型评审和第三方安全测试；支持诊断包由用户预览并主动生成。

## 13. MVP 上线条件

### 13.1 Stable 上线条件

1. GA 与 FR 的 P0 需求全部完成（FR-11 为 P1），UAT-01～UAT-31 全部通过。
2. 个人通用 Agent、单 Runner 协作、GUI、Docker、审批、交接、证据和导出形成闭环。
3. 至少 5 个真实团队完成试点，每队至少 5 个任务。
4. 80% 可用性测试用户无需协助完成核心个人任务和共享交接。
5. 无未解决的高严重度越权、数据泄露或审批绕过问题。
6. 安装、备份、恢复、升级、权限和故障文档完整。
7. 核心指标可统计，发布物满足 MIT 与第三方合规要求。

### 13.2 Federated Beta 对外发布条件

1. FB 的 P0 需求全部完成，UAT-32～UAT-60 全部通过。
2. 默认关闭，三级启用与独立资源 Grant 均生效。
3. 本地节点拒绝超范围请求经过独立验证。
4. 模型外发、跨域传播、派生结果和受限时间线不存在已知绕过。
5. 任意 Shell、直接写回和不支持平台被明确阻断。
6. 支持矩阵、威胁模型、回执、隔离、事件处理和 Beta 限制文档完整。
7. 无未解决的严重或高危安全问题；中低风险有明确处置计划。
8. 至少 5 个封闭试点团队完成真实多环境任务。
9. 具备安全公告、漏洞报告、版本撤回和客户通知机制。
10. 商业页面、销售材料和 GUI 均明确标注 Beta 边界。

### 13.3 Federated GA 转正条件

- 至少 10 个团队完成累计 50 个以上真实多环境任务；
- 至少 8 周持续使用，并有多环境任务复购；
- 独立威胁模型评审和第三方安全测试完成；
- 无未解决严重／高危问题，权限与撤销回归测试持续通过；
- 至少 80% 资源所有者能正确解释读取、外发、成员可见和跨域传播的区别；
- 至少 80% 资源所有者无需管理员代配即可完成常见 Grant；
- 回执完整性、节点兼容性和支持成本达到团队公开承诺；
- 商业团队能够说明 Beta 期间事故、修复与剩余风险；
- 支持范围仅覆盖已验证平台，不以 GA 暗示任意 Shell 或直接写入已自动开放。

任意 Shell、自动写入、内部服务暴露和跨平台等价安全边界均需要各自独立发布评审，不能随联邦 GA 一并默认转正。

### 13.4 立即回滚／停用条件

出现以下任一情况，应暂停新 Grant，必要时主动停用受影响版本：

- 节点可被服务器或其他成员绕过本地授权；
- 未授权文件、模型外发或跨域传播得到确认；
- Grant 撤销、过期或预算耗尽后仍可继续访问；
- 受限结果通过时间线、导出或分析通道泄露；
- 安全回执大量缺失且无法界定影响范围；
- 版本升级静默扩大权限或支持范围；
- 正在利用的高危漏洞无法通过配置快速缓解。

回滚不得删除证据，也不得影响用户导出本人可访问的记录。

## 14. 后续产品规划

### 第一阶段：Stable 核心与封闭只读 Beta

- 完成个人通用 Agent、GUI、Docker Runner 和单 Runner 工作间；
- 完成活证据、无扰接手、档案、MIT 合规和 Stable 商业试点；
- 封闭验证节点配对、只读快照、Grant、模型外发、可见范围、回执和撤销，不开放工具执行。

### 第二阶段：受控工具、Patch 与公开 Federated Beta

- 固定工具模板、参数与预算、结果未知和取消；
- Patch 生成、冲突和本地应用，跨域传播审批；
- 多节点任务计划、外部专家限期参与、策略模板和支持诊断；
- 扩大真实场景试点并完成第三方安全测试。

### 第三阶段：满足条件后的 Federated GA 与场景化产品

- 仅转正已验证资源类型和平台，企业策略、审计、保留与支持服务；
- 根据真实任务数据形成跨环境排障、客户专家诊断等解决方案；
- 就地 Agent 执行、内部服务、远程证明、受控自动写入和更多平台分别独立评估；
- 任意 Shell、自动写入和服务暴露不因 GA 自动开放。

## 15. 产品风险与应对

| 风险 | 表现 | 应对 |
|---|---|---|
| 通用 Agent 底座投入过大，稀释协作差异化 | 大量时间用于追赶成熟客户端的基础功能 | 明确 P0 通用闭环，优先复用执行基础；插件市场和复杂编排不进入 MVP |
| 个人开启共享造成意外泄露 | 私人历史、草稿或凭据被误共享 | 选择性预览、默认排除私人内容、共享状态持续可见并验收转换流程 |
| Docker 部署复杂导致用户流失 | 用户在首个任务前即放弃 | 提供受支持环境基线、状态可见和干净主机验收，统计配置耗时与失败原因 |
| MIT 项目发生第三方许可证或设计侵权 | 复制 LGPL 代码、资产或高度相似界面后错误发布 | 执行第 19 章合规门禁，默认独立设计，任何代码级复用单独评审 |
| 通用平台缺少明确首个任务 | 用户创建后不知道用来做什么 | 首次使用提供示例任务；试点必须携带真实任务；依据数据收敛模板 |
| 多人只围观、不协作 | 在线人数高，但有效协作低 | 以有效协作和交接为指标，强化建议、上下文贡献和审批体验 |
| 单操作者模式被认为不自由 | 多人希望同时指挥 Agent | 保持讨论和建议低门槛，通过试点验证是否确需开放更自由模式 |
| 审批过多影响效率 | 用户等待或要求关闭安全限制 | 区分真实风险与只读操作，优化审批信息和授权范围，跟踪等待时长 |
| 共享上下文越来越多 | Agent 和成员都难以识别重点 | 强调确认事实、决策和待办，提供归档与版本管理，不默认注入全部讨论 |
| 活证据变成额外文档负担 | 用户不愿维护，覆盖率靠强制填写虚高 | 只要求关键结论，允许 Agent 建议来源，跟踪维护耗时与真实复核收益 |
| 无扰问答制造虚假确定感 | 接收者相信摘要而不再核对 | 回答关联来源、明确未知、关键结论人工确认，保留未解决问题清单 |
| 私人接手内容引发隐私争议 | 原操作者或管理员期待可见，接收者期待保密 | 默认私人、发布需主动选择、分析不采正文，并在进入前清楚说明数据边界 |
| 共享导致敏感信息暴露 | 工具输出或文件被不应看到的人获得 | 默认邀请制、明确可见范围、敏感任务拆分工作间、导出受控 |
| 通用协作被现有平台吸收 | 产品变成易复制的附加功能 | 聚焦持续工作、操作权交接、审批和责任记录形成的完整体验，而非分享链接 |

| 把联邦功能做成高权限远控 | 严重安全事故与信任破产 | 本地授权不可绕过，任意 Shell 不进入 Beta |
| 跨节点提示词注入 | 数据横向泄漏 | 来源标签、不可转发、跨域审批和攻击验收 |
| 授权步骤过多 | 所有者疲劳、全部点允许 | 窄模板、合理默认、缩权建议和授权耗时指标 |
| 快照过时与节点离线 | 结论错误或任务中断 | 版本绑定、变化提醒、缓存许可和依赖状态 |
| 结果未知被自动重试 | 重复副作用 | 默认人工核查后重试 |
| 跨平台安全能力不一致 | 虚假安全承诺 | 首期限定支持平台，逐项公布支持矩阵 |
| 联邦价值不足 | 高成本低复购 | 设置商业停止条件，不为叙事强推 |
| Stable 被 Beta 拖垮 | 核心产品无法成熟 | 分轨发布，Stable 独立验收与回退 |

## 18. 差异化调研摘要（2026-11-21）

本章记录功能取舍依据，不把抽样调研包装成“全球没有竞品”的结论。

### 18.1 为什么没有把基础共享能力继续当卖点

共享会话、团队上下文、过程可见、操作交接和审批已经在多类多人 Agent 产品中出现。继续增加类似功能可以提高完整度，但难以回答“客户为什么换用 Unspool”。因此，本版将它们保留为基础设施，把差异化集中到可信结果和接手效率。

### 18.2 为什么没有选择“成功会话一键变工作流”

该方向有商业价值，但已不再是明显空白。例如 [CREAO 已公开描述从成功聊天会话创建可复用 Agent](https://creao.ai/features/ai-agents)，多款工作流产品也支持模板、复制和自动化。Unspool 可以将任务模板作为 P1 完整度功能，但不把它作为首要卖点。

### 18.3 为什么选择活证据

近期关于 Agent 证据溯源的讨论，已从“记录输出来自哪里”推进到“来源变化后哪些判断会失效”。[O’Reilly 对决策血缘的讨论](https://www.oreilly.com/radar/when-ai-generated-data-becomes-tomorrows-ground-truth/)明确区分了数据来源与组织基于该来源采取的行动；[Agent 证据溯源研究](https://arxiv.org/html/2606.04990v1)也将陈旧、冲突和失效列为记忆溯源的重要问题。

Unspool 的产品机会不是再做一个引用列表，而是把**来源状态、业务决策、完成验收和返工范围**连起来。其商业假设是：高复核成本团队愿意为减少错误决策和重复核查付费。该假设仍需通过试点验证。

### 18.4 为什么选择无扰接手

结构化交接摘要、完整记录和下一步建议已经较常见，例如 [Taskade 的交接讨论](https://www.taskade.com/blog/agent-handoff-explained)也强调结构化摘要、未决问题和证据，而非传递整段对话。

Unspool 进一步把“接收者准备”设为独立产品阶段：接受责任之前可以私人提问、核对来源、保留未解决问题，再决定是否公开澄清和接受操作权。差异化不在“又一种摘要”，而在**不干扰现任操作者的准备过程及其责任确认**。该卖点应以减少同步会、追问和接手后返工作为验证依据。

### 18.5 命名说明

Unspool 原意是展开线轴、影片或缠绕的线索。对本品而言，它有三层对应：把长任务的完整过程逐步展开，把纠缠的事实、决策与证据理顺，把一个人的工作清晰地传递给下一个人。名称不直接描述“工作平台”，而是表达产品使用后的感受——复杂工作变得可见、可懂、可接续。

产品口号为“复杂工作，清晰展开”。初步检索未发现与目标品类明显冲突的知名产品，但这不构成商标、域名或法律可用性保证，正式商用前仍需专项核验。

### 18.6 PI-Desktop 参考与许可证核查

PI-Desktop 提供了持续项目／会话、独立桌面工作空间、模型选择、工具过程和右侧工作面板等成熟交互范例。这些抽象交互思想与 Unspool 的通用 Agent 底座相关，因此可以作为设计研究输入。

但其[官方许可证](https://github.com/vastsa/PI-Desktop/blob/main/LICENSE)为 **LGPL-3.0**。这意味着 Unspool 不能把其源码或资产复制后简单改为 MIT 发布；若未来发生代码级复用，必须单独评估并履行相应义务。MVP 默认采用独立 GUI 设计与实现，不 fork PI-Desktop，也不复刻其具有识别性的视觉表达。

### 18.7 联邦式环境协作的可行性依据

单 Runner 工作间不能解决资源不宜集中、环境无法复制和外部专家不应获得长期账号的问题。Unspool 的联邦模式并非完全无中心，而是让数据与执行能力分布在不同所有者域中，协调方不再天然拥有全部权限。

- [OpenClaw 节点文档](https://docs.openclaw.ai/nodes/index.md)展示了节点配对、能力声明和扩大能力重新审批。
- [Teleport 按需访问](https://goteleport.com/docs/identity-governance/access-requests/)验证了短期身份、限时授权和审计路径。
- [GitHub 自托管 Runner 安全说明](https://docs.github.com/en/actions/concepts/runners/self-hosted-runners)说明不可信工作流可能持久攻陷环境，因此 Beta 不默认开放任意 Shell。
- [OWASP Prompt Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)支持最小权限和高风险人工审批。
- [Bazel Docker Sandbox](https://bazel.build/remote/sandboxing)为明确输入输出和干净执行边界提供参照。

这些资料证明组件可行，不证明组合后天然安全；跨域数据流和用户理解仍需 Unspool 自行验证。

## 19. MIT 开源与第三方合规需求

### 19.1 自有项目的许可范围

1. Unspool 自有源代码计划在仓库根目录提供 MIT License 和明确版权声明。
2. MIT 只适用于项目有权授权的自有内容，不自动覆盖第三方库、字体、图标、图片、模型、数据集、商标或用户内容。
3. Unspool 名称和标识即使与代码同仓库发布，也应单独说明品牌使用边界，避免让 MIT 被误解为商标授权。
4. 文档、示例、设计资源和宣传素材分别核查来源，不因源代码采用 MIT 而默认全部可自由复用。

### 19.2 第三方内容清单与审查

发布前必须建立并维护第三方清单，范围至少包括：

- 直接与间接软件依赖；
- GUI 组件、字体、图标、插画和截图；
- Docker 基础镜像及随镜像分发的软件；
- 插件、工具、模板和文档中的外部代码片段；
- 用于宣传或内置示例的外部内容。

清单至少记录名称、版本、来源、许可证、版权信息、使用位置、是否修改及需要保留的通知。许可证未知、来源不清或无权使用的内容默认阻断发布，而不是先发布后补查。

对于 GPL、AGPL、LGPL 等具有额外义务的组件，必须单独评审其使用与分发方式，不能简单理解为“与 MIT 兼容，所以可以直接复制并以 MIT 重新授权”。MIT、BSD、Apache 等许可内容也需要保留各自要求的版权和许可声明。

### 19.3 PI-Desktop 的专项边界

MVP 默认遵守以下规则：

1. 不复制 PI-Desktop 的前端或宿主源码、组件、样式表和构建产物。
2. 不在产品或宣传物中直接复用其图标、插画、截图、动画、文案和品牌元素。
3. 不做像素级复刻，也不通过简单换色、替换 Logo 来制造“原创界面”。
4. 只参考抽象功能与交互概念，具体信息层级、视觉语言、组件表现和品牌识别由 Unspool 独立设计。
5. 设计过程保留参考来源、设计差异和原创记录，发布前进行相似性与资产来源审查。
6. 若未来确需引入 PI-Desktop 代码，必须作为独立变更进行 LGPL-3.0 合规评审，明确源代码提供、修改说明、通知、分发及其他适用义务；不得默认进入 MIT 核心发布。

### 19.4 社区贡献要求

- 贡献者需确认自己有权提交相关内容，并同意项目按 MIT 许可其自有贡献。
- 不接受来源不明、从其他项目直接复制但未保留许可义务的代码或资产。
- 引入新依赖或设计资产时同步更新第三方清单，不在发布前集中补账。
- 对重大第三方许可风险进行专项复核，必要时寻求法律／合规意见。

### 19.5 开源发布物检查

每次公开发布至少检查：

1. MIT License 和版权信息存在且与项目实际一致；
2. 第三方清单及必要通知随发布物提供；
3. 具备可审计的依赖与资产清单，可采用 SBOM 或等效形式；
4. 不包含个人凭据、私有任务、内部地址、用户数据或测试秘密；
5. 内置示例、图标、字体、截图和文档均有明确来源与使用权；
6. Docker 发布内容与清单一致，不因镜像打包绕过第三方义务；
7. 参考产品合规检查完成，没有将 PI-Desktop 的 LGPL 内容误标为 Unspool 的 MIT 原创内容。

## 结语

Unspool 的成熟不取决于一次跨节点执行演示，而取决于三个连续成立的产品事实：

1. **个人用户愿意把它当作日常通用 Agent。**
2. **团队愿意把高价值工作放进共享工作间，因为上下文、证据、审批和交接更可靠。**
3. **资源所有者愿意贡献原本不会上传的环境能力，因为他们能控制范围、接收方、期限、传播和撤销。**

联邦式协作的护城河不是连接更多机器，而是把设备级、账号级、长期的宽泛信任，转化为任务级、能力级、短期、可撤销且可验证的协作信任。

如果 Stable 尚未成熟，不用联邦 Beta 掩盖；如果 Beta 尚未证明真实价值与安全可控，不用“划时代”推动转正。只有用户持续完成真实多环境任务，并愿意再次贡献自己的环境，Unspool 才从好产品设想变成商业项目。
